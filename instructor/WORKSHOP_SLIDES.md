# ワーク案内スライド原稿

## スライド1：個人の変更をチームの成果として届ける

### 画面に表示する内容

```text
チームで方針を揃える
個人で実装する
お互いにレビューする
チームで公開を判断する
```

### 講師が伝えること

このワークでは、個人でコードを書くだけでなく、変更をチームの成果として公開するまでを体験します。

## スライド2：ワークのゴール

### 画面に表示する内容

- 1人1機能を実装し、Pull Requestを作成する
- 別の参加者の変更をレビューする
- CI/CDの結果とレビューを基に、チームで公開を判断する
- 公開後に、AIへ任せたことと人間が判断したことを共有する

## スライド3：ワーク全体は80分

### 画面に表示する内容

```text
チームリポジトリの準備：20分
開発、レビュー、公開：60分
```

### 講師が伝えること

最初の20分で開発場所と自動化を準備します。
全員の準備が終わってから、60分の開発ワークを開始します。

## スライド4：セットアップは代表者が操作する

### 画面に表示する内容

| 代表者 | ほかのメンバー |
|---|---|
| 画面共有する | GitHubユーザー名を伝える |
| GitHubを設定する | 招待を承認する |
| Issueを作成する | 自分のIssueを確認する |
| 進捗をチームへ伝える | 最後にリポジトリを取得する |

### 講師が伝えること

GitHubの設定は代表者だけが操作します。
複数人で同時にSettingsを変更しないでください。

## スライド5：テンプレートからチーム用リポジトリを作る

### 画面に表示する内容

```text
Use this template
→ Create a new repository
→ Public
→ team-idea-board-チーム番号
```

### 講師が伝えること

テンプレートリポジトリのURLをチャットへ共有します。
代表者は画面を共有したまま操作してください。

## スライド6：チーム全員をCollaboratorへ追加する

### 画面に表示する内容

```text
Settings
→ Collaborators
→ Add people
```

### 完了条件

全員が招待を承認し、チーム用リポジトリを開ける。

## スライド7：CIとGitHub Pagesを動かす

### 画面に表示する内容

```text
Actions → CI → Run workflow
Settings → Pages → Source：GitHub Actions
Actions → Deploy to GitHub Pages → Run workflow
```

### 完了条件

- `quality`が緑色になっている
- 公開URLでサンプルアイデアが3件表示される

### 講師が伝えること

赤くなった場合は設定を変更せず、失敗したStepを開いて講師を呼んでください。

## スライド8：`main`を保護する

### 画面に表示する内容

- Pull Requestを必須にする
- 1名のApproveを必須にする
- Status check `quality`を必須にする
- 未解決の会話がある場合はマージできないようにする

### 講師が伝えること

この設定によって、実装者だけの判断では`main`へ変更を取り込めなくなります。

## スライド9：Issueとレビュー相手を決める

### 画面に表示する内容

| 人数 | 作成するIssue | レビュー順 |
|---|---|---|
| 3人 | Ticket A、B、C | A→B→C→A |
| 4人 | Ticket A、B、C、D | A→B→C→D→A |

Issueテンプレートを選び、実装担当者をAssignする。

## スライド10：全員がローカルで確認する

### 画面に表示する内容

```bash
gh repo clone リポジトリ所有者/team-idea-board-チーム番号
cd team-idea-board-チーム番号
npm ci
npm run check
```

### 完了条件

全員の`npm run check`が成功する。

## スライド11：開発ワークを始められる状態

### 画面に表示する内容

- 全員が同じリポジトリへ参加している
- CIと公開URLを確認できる
- `main`が保護されている
- 担当Issueとレビュー相手が決まっている
- 全員のローカル確認が成功している

1つでも終わっていない場合は、開発を始めず講師を呼ぶ。

## スライド12：チームで実装方針を揃える

### 画面に表示する内容

```text
私はTicket ○を担当します。
○○を変更し、○○という操作とテストで確認します。
ほかの変更へ影響しそうな箇所は○○です。
```

1人30秒で共有する。

## スライド13：個人で実装する

### 画面に表示する内容

- 1人1 Issue
- 1人1 Branch
- 1人1 Pull Request
- 担当外の機能は変更しない
- 既存の`it.todo`をテストへ置き換える
- `npm run check`まで実行する

## スライド14：Pull Requestで変更を説明する

### 画面に表示する内容

- 何を変更したか
- チームで確認した方針
- AIが提案したこと
- 人間が判断したこと
- 確認した操作とテスト

## スライド15：別の参加者がレビューする

### 画面に表示する内容

- 受け入れ条件を満たしているか
- 画面上で期待した変化を確認できるか
- 既存機能が壊れていないか
- CIが成功しているか
- 実装者が変更を説明できるか

確認した事実をコメントとして残す。

## スライド16：チームで公開を判断する

### 画面に表示する内容

```text
受け入れ条件を満たしている
＋ CIが成功している
＋ 他者レビューが完了している
＋ 実装者が説明できる
＝ マージしてよい
```

Pull Requestを1本ずつマージする。

## スライド17：公開結果と学びを共有する

### 画面に表示する内容

- 公開URLで全員分の機能を確認する
- AIへ任せてうまくいったこと
- 人間が判断する必要があったこと
- 他者のレビューで気づいたこと
- 次に改善したいこと

各自が1つを選び、30秒で共有する。
