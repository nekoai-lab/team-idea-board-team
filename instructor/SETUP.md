# 講師用セットアップ

## 1. チームごとのPublicリポジトリを作成する

このリポジトリをGitHub Template Repositoryに設定し、チームごとに複製します。

例：

```text
team-idea-board-01
team-idea-board-02
team-idea-board-03
```

サンプルデータのみを使用し、秘密情報や個人情報を含めないでください。

## 2. 参加者をCollaboratorへ追加する

各チームの参加者にWrite権限を付与します。講義前日までに、全員がリポジトリを開けることを確認します。

## 3. Issueを作成・割り当てる

`instructor/tickets/`の本文を使ってIssueを作成します。

- 3人チーム：Ticket A・B・C
- 4人チーム：Ticket A・B・C・D

Issueは事前に各参加者へAssignしてください。

レビュー相手も事前に決めます。

- 3人チーム：A→B→C→A
- 4人チーム：A→B→C→D→A

## 4. GitHub Pagesを有効にする

Repository Settings → Pages → Build and deployment → Sourceで「GitHub Actions」を選択します。

`main`へPushされると、`.github/workflows/deploy-pages.yml`が検証とデプロイを実行します。

## 5. `main`を保護する

Repository Settingsから、`main`に次を設定します。

- Pull Requestを必須にする
- 1名以上のApproveを必須にする
- Status check `quality`の成功を必須にする
- 未解決の会話がある場合はマージ不可にする

## 6. 事前動作確認

講師アカウントで以下を確認します。

```bash
npm ci
npm run check
```

確認項目：

- スターターのCIが成功する
- 4件のTicketテストが`todo`として表示される
- Pull Requestテンプレートに、チーム方針と人間の判断を書く欄がある
- `main`へのPushでGitHub Pagesが公開される
- 公開URLでサンプルアイデア3件が表示される

## 当日の進行

### 0〜8分：チームで方針を揃える

各参加者に、担当Issue、完成条件、主な変更箇所、影響しそうな箇所を30秒で説明してもらいます。
この時間はコードを書かず、各自の担当範囲とマージ条件を揃えます。

### 8〜28分：個人で実装する

各参加者が自分のBranchで実装します。
講師は、担当外の変更を始めていないか、既存の`it.todo`をテストへ置き換えているかを確認します。

### 28〜50分：Pull Requestと相互レビュー

28分時点でPull Request作成を案内し、33分時点でレビューへ切り替えます。
レビューでは、確認した事実を1件以上コメントとして残してもらいます。

### 50〜55分：チームで公開を判断する

各Pull Requestについて、実装者とレビュアーが次の内容を説明します。

```text
実装者：変更内容、確認方法、AIの提案に対する判断
レビュアー：確認した操作、テスト、公開可能と判断した理由
```

チーム内で異論がなければ、Pull Requestを1本ずつマージします。
同時に複数のPull Requestをマージしないよう案内します。

### 55〜60分：公開結果と学びを共有する

GitHub Pagesの公開URLで全員分の機能を確認します。
最後に、各参加者が次のうち1つを共有します。

- AIへ任せてうまくいったこと
- 人間が判断する必要があったこと
- 他者のレビューで気づいたこと
- 次に改善したいこと

## 当日の復旧方針

- 方針確認が長引いた場合：各自の説明を30秒に区切り、未解決事項だけを残す
- 実装が止まった場合：受け入れ条件を1つに絞る
- コンフリクトした場合：対象PRを最新の`main`から作り直し、変更ファイルだけを移す
- CIが失敗した場合：Actionsの最初の失敗箇所をAIへ渡して原因を説明させる
- デプロイが失敗した場合：`main`のCI成功を確認し、Deploy workflowを再実行する
- 時間切れの場合：完成したPRだけをマージし、未完了IssueはCloseせず残す
